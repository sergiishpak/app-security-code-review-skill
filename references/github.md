# GitHub issue and private disclosure workflow

1. Ask which report findings the user wants to track if they have not chosen. Verify the destination repository, its visibility, and the relevant security policy. For disclosure-safe items, check existing issues for duplicates and group findings when they share one fix. Keep unresolved vulnerability details out of public issues, comments, and search queries. Use the verified private reporting channel or the maintainer's draft advisory route for unresolved vulnerabilities in public repositories. If visibility or access is uncertain, keep the draft in chat until a private destination is verified. [GitHub private reporting guidance](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately)
2. Draft a self-contained title and body. Include the finding and severity rationale, affected component and revision, actual implementation, design cause when supported, expected behavior with exact pinned OWASP guidance, plain-language impact, proposed fix, and how to verify it. Include immutable GitHub code permalinks with line numbers where the reviewed revision is available remotely. For local-only changes, use file and line references and identify the evidence as local. Redact secrets and sensitive data.
3. Present the exact title, body, repository, channel, and visibility for each draft. Post only the approved drafts to the approved destinations. If the content or destination changes materially, show the revised draft for approval. When tooling or permissions prevent posting, hand back the approved draft and its intended destination.
4. Read back the created item and return its link and visibility in chat. If creation returns an uncertain result, check for an existing item before retrying.
