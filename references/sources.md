Cite ASVS as `v<version>-<requirement ID>`. Cite MASVS by control ID and version. Use the edition year for Top 10 categories and cite them as risk categories. Identify supplemental entries by ID or title and by the pinned tag or commit. Open the pinned source and link the specific control, category, or section. If it has no stable anchor, link the versioned document and name the section.

For a user-requested MAS testing profile, consult the [official profile catalog](https://mas.owasp.org/Profiles/). A profile may evolve separately from MASVS. Record the profile and exact source revision defining its mapping, and check that the IDs match the pinned controls and any supplemental material cited. If the mapping cannot be verified, ask to review an explicit MASVS control set instead. Apply the same care when crossing MASWE and MASTG versions, since MASWE v1.0.0 renumbered its pre-release IDs. Use the official [MASWE v1.0.0 migration mapping](https://github.com/OWASP/maswe/releases/download/v1.0.0/OWASP_MASWE.yaml) and check the scope of the mapped entry before citing it. If you cannot verify the mapping, cite the pinned MASVS control directly and mark the supplemental mapping unverified.

These references link to upstream works. The repository distributes original workflow instructions. OWASP project names identify the sources. The skill is independent of the OWASP Foundation. See the [OWASP branding guidelines](https://owasp.org/policy/branding-guidelines).
